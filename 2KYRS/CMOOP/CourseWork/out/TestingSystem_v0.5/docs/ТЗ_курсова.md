# ТЕХНІЧНЕ ЗАВДАННЯ
## на курсову роботу «Розробка WPF-застосунку для автоматизованого контролю знань та проведення тестування»

## 1. Загальні відомості

1.1. **Назва роботи:** Розробка WPF-застосунку для автоматизованого контролю знань та проведення тестування (робоча назва програми — Testing System).
1.2. **Замовник:** кафедра (заклад вищої освіти) — в особі викладача, який перевіряє курсову роботу.
1.3. **Виконавець:** студент (автор курсової роботи).
1.4. **Підстава для розробки:** навчальний план дисципліни, завдання на курсову роботу.
1.5. **Плановий строк:** відповідно до графіка навчального процесу (орієнтовно 8–10 тижнів, див. розд. 6).

## 2. Призначення розробки

2.1. Програма призначена для автоматизації контролю знань студентів: створення тестів і лекцій, проведення компʼютерного тестування, автоматичної та ручної перевірки робіт, ведення журналу успішності й аналітики.
2.2. Користувачі системи:
- **Студент** — проходить призначені тести, переглядає лекції, власні результати та розбір помилок, отримує PDF-сертифікати;
- **Викладач** — створює тести й лекції, перевіряє роботи, що потребують ручної оцінки, аналізує успішність;
- **Адміністратор** — має права викладача та додатково керує навчальними групами.
2.3. Цілі автоматизації: скоротити час викладача на перевірку, стандартизувати оцінювання, унеможливити списування під час тестування, дати студенту швидкий зворотний звʼязок.

## 3. Вимоги до програмного виробу

### 3.1. Загальна архітектура

3.1.1. Платформа: **WPF (.NET 10, Windows)**, мова C#, патерн **MVVM**.
3.1.2. Шари застосунку: `Abstractions` (інтерфейси) → `Services` (бізнес-логіка) → `Persistence` (сховище) → `ViewModels` / `Views` (інтерфейс). Залежності звʼязуються через DI-контейнер (`Microsoft.Extensions.DependencyInjection`) в єдиній точці — `App.xaml.cs`.
3.1.3. Сховище на етапі курсової — **in-memory репозиторії** з можливістю заміни на SQLite / PostgreSQL через EF Core **без змін бізнес-логіки** (міняються лише реєстрації в DI). Демо-дані створює `DemoDataSeeder`.
3.1.4. Мова інтерфейсу — **українська за замовчуванням**, з перемикачем UA/RU/EN «на льоту» (таблиця `Strings.cs`, розширення `{loc:T …}`). Світла/темна теми.

### 3.2. Користувачі, автентифікація, безпека

3.2.1. Вхід за логіном і паролем; реєстрація доступна лише студентам (з вибором навчальної групи). Демо-акаунти: `teacher`, `student1`, `student2`, `admin` (пароль `1234`).
3.2.2. Паролі зберігаються лише у вигляді гешу **PBKDF2 із сіллю**; перевірка довжини, підтвердження зміни пароля.
3.2.3. Блокування сеансу після 30 хв бездіяльності (пароль для розблокування, ліміт спроб, примусовий вихід).
3.2.4. API-ключі AI-провайдерів зберігаються **зашифрованими (DPAPI, лише поточний користувач Windows)** у `%AppData%\TestingSystem\ai-settings.json`; віддалені сервери — лише через HTTPS (http дозволено тільки для localhost).
3.2.5. Доступ за ролями: студент не має доступу до вікна викладача; викладач керує лише власними тестами; керування групами — лише адміністратор.

### 3.3. Конструктор тестів (викладач)

3.3.1. Налаштування тесту: назва, опис, ліміт часу (0 — без ліміту), прохідний бал %, число спроб (0 — безліміт), перемішування питань і варіантів, показ пояснень студенту, пін-код доступу, призначення групам (порожньо — усім).
3.3.2. Типи питань (6): **один варіант, кілька варіантів, текстова відповідь, відповідність (пари), послідовність, завантаження файлу** (до 10 МБ; дозволені документи, зображення, архіви, вихідний код).
3.3.3. Текстова відповідь: точний збіг / містить фразу / ручна перевірка; пари — унікальність правих частин; послідовність зберігається у правильному порядку, студент бачить перемішаною.
3.3.4. Кожне питання: текст, макс. бал, зображення (опційно), пояснення. Валідація як у ручному конструкторі.

### 3.4. Проведення тестування (студент)

3.4.1. Картки доступних тестів: час, число питань, прохідний бал, використані спроби, мітка пін-коду. Захищені тести — через діалог пін-коду (демо-пін `1234`).
3.4.2. Проходження: навігація питаннями, лічильник відповідей, таймер із попередженням «менше хвилини», підтвердження здачі (з числом питань без відповіді).
3.4.3. **Античит:** втрата фокуса / згортання вікна — порушення; після N порушень тест здається автоматично. Лічильник порушень фіксується в результаті.
3.4.4. Підсумок одразу: складено/не складено (бали, %) або попередній результат, якщо частина відповідей чекає викладача.

### 3.5. Перевірка робіт (викладач)

3.5.1. Черга робіт зі статусом «на перевірці»; файл відповіді відкривається; бал у межах максимуму; примітка; завершення переводить роботу в «завершено».
3.5.2. AI-підказки оцінювання відкритих відповідей (кнопка «AI: запропонувати оцінки») — лише пропозиції, рішення за викладачем. Файли AI не читає.

### 3.6. Лекції

3.6.1. Викладач: створення/редагування (Markdown: заголовки, списки, код), чернетка/публікація, привʼязка рекомендованого тесту, генерація чернетки через AI за назвою.
3.6.2. Студент: читання опублікованих лекцій своєї групи, перехід до рекомендованого тесту.

### 3.7. AI-помічник

3.7.1. Провайдери-стратегії (`IAiProvider`): **Mock** (офлайн-демо), **OpenAI-сумісний** (OpenAI, OpenRouter, Ollama, LM Studio), **Anthropic**, **Google Gemini**. Вибір — у налаштуваннях, без змін коду; новий провайдер додається за інструкцією `docs/AI_PROVIDERS.md`.
3.7.2. Функції: пропозиція тем лекцій → генерація лекції → генерація тесту (валідація питань тими ж правилами, биті відкидаються з лічильником) → підказки оцінок. Усе створене AI відкривається **в редакторах як чернетка** для перевірки.
3.7.3. Мова відповідей AI = мова інтерфейсу. У вікні налаштувань — вбудована інструкція з підключення. Кнопка «Перевірити зʼєднання» (очікується `OK`).
3.7.4. Приватність: зовнішньому провайдеру передаються лише тексти матеріалів і відповіді **без імен**; попередження показано в UI.

### 3.8. Журнал, аналітика, експорт

3.8.1. Таблиця результатів із фільтрами за групою/тестом; статуси: виконується / на перевірці / завершено / час вичерпано.
3.8.2. Складність питань (підсвітка питань із ≥50 % неповних відповідей), середні бали, відсоток складання, статистика за групами, динаміка студента.
3.8.3. Експорт: **Excel, CSV, звіт PDF** (`QuestPDF`); **PDF-сертифікат** за успішно складений і перевірений тест. Розбір помилок студента з правильними відповідями (якщо викладач дозволив).

### 3.9. Керування групами (адміністратор)

3.9.1. Окрема вкладка «Групи»: список із числом студентів, додавання (перевірка порожньої назви та дублікату), видалення з підтвердженням.
3.9.2. Групу зі студентами видаляти заборонено — з поясненням перевести студентів до інших груп.

### 3.10. Нефункціональні вимоги

3.10.1. Продуктивність: старт < 3 с на типовому ПК; генерація звітів до 1000 рядків < 5 с; таймаут AI-запитів 5–300 с (налаштовується).
3.10.2. Надійність: некоректні відповіді AI відкидаються валідацією, а не падають; пошкоджений файл налаштувань → безпечний Mock-режим; недоступність AI не блокує основні функції.
3.10.3. Супроводжуваність: OCP для провайдерів AI та сховищ; рядки UI — в одному місці; код з українськими XML-коментарями до публічних типів.

## 4. Вимоги до апаратного та програмного забезпечення

4.1. ОС Windows 10/11 (x64); встановлений .NET 10 Desktop Runtime; ~100 МБ вільного місця; для AI-функцій (крім Mock) — доступ до інтернету.
4.2. Середовище розробки: Visual Studio 2022+ або VS Code + .NET 10 SDK; збірка — `dotnet build TestingSystem.csproj`.

## 5. Вимоги до інтерфейсу користувача

5.1. Два робочі вікна за роллю (кабінет студента / місце викладача), вікно входу та реєстрації, модальні редактори тестів і лекцій, діалоги підтверджень українською.
5.2. Єдина шапка з профілем, перемикачами мови/теми та індикатором підключення; прогрес-бари під час AI-операцій з можливістю скасування.

## 6. Етапи розробки (орієнтовний план)

## 7. Порядок контролю та приймання

7.1. Перевірка сценаріїв: реєстрація студента → створення тесту з усіма типами питань → призначення групі → проходження (в т.ч. порушення фокуса) → автоперевірка → ручна перевірка → аналітика/експорт/сертифікат → генерація лекції й тесту через AI (Mock і реальний провайдер).
7.2. Граничні випадки: порожній тест, вичерпані спроби, невірний пін-код, файл > 10 МБ, дублікат групи, видалення групи зі студентами, недоступний AI-сервіс, пошкоджений JSON від AI.
7.3. Приймання — демонстрація роботи програми та захист пояснювальної записки (опис архітектури, моделей, алгоритмів оцінювання й античиту, інструкція користувача).

## 8. Вимоги до документації

8.1. Пояснювальна записка: постановка задачі, огляд аналогів, проєктування (діаграми сутностей, структура шарів), реалізація ключових алгоритмів, тестування, інструкція користувача, висновки.
8.2. Вихідний код з коментарями; файл `docs/AI_PROVIDERS.md` — інструкція з підключення та додавання AI-провайдерів.

## 9. Розподіл робіт між двома виконавцями

Спільне (роблять разом на старті, ~0,5 тижня): п. 1–2 ТЗ, контракт моделей (`Models/Entities.cs`, `Models/Enums.cs`) та інтерфейсів (`Abstractions/`), домовленість про DI в `App.xaml.cs`, спільне тестування й пояснювальна записка в кінці.

### Виконавець 1 — «Ядро тестування» (клієнтський цикл студента + конструктор)

1. Архітектура, DI-контейнер, in-memory репозиторії, `DemoDataSeeder`.
2. Автентифікація та ролі (`AuthService`, PBKDF2), вікна входу/реєстрації, профілі, зміна пароля.
3. Блокування сеансу після бездіяльності (`InactivityMonitor`, `SessionLockService`).
4. Конструктор тестів: усі 6 типів питань, валідація, налаштування (час, спроби, пін-код, призначення групам, перемішування).
5. Проходження тестів: сесії (`TestSessionService`, `TestSessionController`), таймер, античит (втрата фокуса/згортання, автоздача), `GradingEngine` (автоперевірка всіх типів).
6. Кабінет студента: доступні тести, «Мої результати», розбір помилок, PDF-сертифікат.
7. Локалізація своєї частини, світла/темна тема у своїх вікнах.

### Виконавець 2 — «Контент, аналітика та AI» (робоче місце викладача + інтелект)

1. Лекції: CRUD, Markdown-редактор і перегляд, чернетка/публікація, привʼязка рекомендованого тесту.
2. Керування групами для адміністратора (додавання, видалення з перевірками).
3. Перевірка робіт викладачем: черга, бали, примітки, статуси, AI-підказки оцінок.
4. Журнал і аналітика: фільтри, складність питань, статистика за групами, динаміка.
5. Експорт Excel/CSV, звіт PDF, генератор сертифікатів (`ReportExportService`, `CertificateHelper`).
6. AI-помічник повністю: `IAiProvider`-стратегії (Mock, OpenAI-сумісний, Anthropic, Gemini), `AiClientRouter`, `AiAssistant`, промпти, валідація (`AiTestMapper`), налаштування з DPAPI-шифруванням, вбудована інструкція.
7. Таблиця рядків `Strings.cs` (UA/RU/EN) для своєї частини, теми у своїх вікнах, `docs/AI_PROVIDERS.md`.

### Чому поділ рівний

| Критерій | Виконавець 1 | Виконавець 2 |
|---|---|---|
| Великих підсистем | 2 (конструктор, проходження) | 2 (аналітика+експорт, AI-помічник) |
| Середніх підсистем | 2 (auth+профілі, кабінет студента) | 3 (лекції, перевірка робіт, групи) |
| Інфраструктура | DI, сховище, сідер, блокування сеансу | Сервіси експорту, AI-інфраструктура, строки |
| Орієнтовна трудомісткість | ~50 % | ~50 % |

Межа інтеграції: Виконавець 1 віддає стабільні `Test`, `Question`, `TestSessionService`, `GradingEngine`, статуси `ResultStatus`; Виконавець 2 їх лише споживає (перевірка, аналітика, AI-генерація через ті самі правила валідації). Обидва не змінюють чужі файли без узгодження.
